===============================================================
Moon_Dance 智能坐垫小程序 — 后端 API 接口对接文档
===============================================================
前端同学请参照此文档进行小程序端开发对接。
后端基础地址（本地开发）: http://localhost:5000
后端基础地址（云端部署）: https://www.myhjmycjh.tech
统一 API Key: myh

所有接口统一响应格式：
{
    "ok": true/false,
    "message": "描述信息",
    "data": { ... }   // 成功时返回具体数据，失败时为 null
}

重要说明：
  - 小程序前端不需要处理 simulator 上传时的 `encrypted_payload`
  - 如果你看到 `gAAAAA...` 这一类字符串，那是设备上传接口里的 Fernet 加密密文，不是小程序业务接口的返回格式
  - 该密文由服务端在上传入口自动解密，小程序前端不需要自己做解密逻辑
  - 小程序应只对接本文档中的 `/api/miniapp/*` 接口，不要把设备上传包体当成页面展示数据
  - 从当前版本开始，同一个 `device_id` 只允许绑定一个用户；如果新用户重新绑定同一设备，系统会自动解除旧用户的该设备绑定

===============================================================
乱码问题专项说明（可直接转发给前端同学或 AI）
===============================================================

下面这段话可以直接复制给前端同学：

【问题说明】
你现在看到的 `gAAAAA...` 不是接口返回乱码，也不是后端返回格式错误，而是本地模拟器 `simulator_client.py` 上传数据时使用 Fernet 做强加密后产生的密文字符串。

【重点结论】
1. 这个 `gAAAAA...` 只会出现在“设备上传接口”的请求体里
2. 服务端收到后会自动解密
3. 小程序前端不需要自己解密
4. 小程序页面不要读取 `encrypted_payload`
5. 前端只需要调用 `/api/miniapp/*` 这些业务接口

【为什么会看到这个字符串】
如果前端看到 `gAAAAA...`，通常说明前端当前拿到的是：
- 模拟器上传接口的原始请求体
- 上传调试包里的 `encrypted_payload`
- 或者把“上传协议”误当成“小程序查询接口返回”了

而不是拿到了真正给小程序页面使用的业务接口响应。

【正确的前端接入方式】
前端页面请只对接以下接口：
- `POST /api/miniapp/user/register`
- `POST /api/miniapp/user/login`
- `GET /api/miniapp/device/<device_id>/realtime`
- `GET /api/miniapp/user/<user_id>/stats`
- `GET /api/miniapp/leaderboard`
- `PUT /api/miniapp/user/<user_id>/settings`

这些接口返回的都是正常 JSON，可直接用于页面渲染，不会要求前端处理 `gAAAAA...` 这种密文。

【后端当前实际行为】
本地 simulator 默认会加 `--encrypt` 参数，所以发到上传接口时，包体可能是：
{
  "encrypted_payload": "gAAAAABqAEEW4Qpsl2Kvr0zyVg7fMGJOcj6wuVaIGwWFb9tabMgitWy..."
}

服务端上传入口收到这个字段后，会先自动解密，再继续做：
- request_id 校验
- 幂等去重
- 日志写入
- 异步处理

所以：
- 上传端可以加密
- 服务端负责解密
- 前端不负责解密

【如果前端/AI 要排查，应该这样判断】
请先确认当前拿到的数据到底来自哪一个接口：

1. 如果是 `/api/v1/upload`、`/api/v2/ingest`、`/api/upload_data`
   - 这是设备上传接口
   - 看到 `encrypted_payload` 是正常现象
   - 这不是前端页面应该直接消费的数据

2. 如果是 `/api/miniapp/*`
   - 返回应该是正常 JSON
   - 不应该出现 `gAAAAA...`
   - 如果出现了，说明前端实际请求地址很可能配错了，或者读错了数据源

【请前端/AI 直接按这个方向修正】
请不要再尝试在小程序前端解密 `gAAAAA...`。
请检查当前前端代码是否错误读取了上传接口数据，或错误使用了 simulator 的上传包体。
请把前端页面数据源统一改为 `/api/miniapp/*` 业务接口响应。

【一句话总结】
`gAAAAA...` 是上传密文，不是小程序页面数据；服务端会自动解密，前端不要自己解，前端只接 `/api/miniapp/*`。

下面这段可以直接复制给对方的 AI：

请帮我检查当前前端代码是否错误地把设备上传接口（`/api/v1/upload`、`/api/v2/ingest` 或 simulator 上传包体）当成了小程序页面数据源。  
当前后端的 `simulator_client.py` 默认会发送 Fernet 加密后的 `encrypted_payload`，密文形如 `gAAAAA...`。这类密文由服务端上传入口自动解密，前端小程序不需要实现解密逻辑。  
请把前端页面数据源统一改为 `/api/miniapp/*` 接口，包括注册、登录、realtime、stats、leaderboard、settings。  
如果当前页面里出现 `gAAAAA...`，请优先排查：
1. 是否请求错了接口地址  
2. 是否把上传请求体当成了页面展示数据  
3. 是否把 simulator 调试数据误当成了小程序接口返回  
目标是让前端只消费正常 JSON 业务响应，而不是消费 `encrypted_payload` 密文。

===============================================================
一、鉴权机制说明（必须先看）
===============================================================

小程序接口现已升级为“双重鉴权”：
  1. X-API-Key: myh
  2. Authorization: Bearer <token>

鉴权规则：
  - 注册接口 `POST /api/miniapp/user/register`
    只要求请求头带 `X-API-Key: myh`
  - 登录接口 `POST /api/miniapp/user/login`
    只要求请求头带 `X-API-Key: myh`
  - 以下接口必须同时带上两种请求头：
    · GET /api/miniapp/device/<device_id>/realtime
    · GET /api/miniapp/user/<user_id>/stats
    · GET /api/miniapp/leaderboard
    · PUT /api/miniapp/user/<user_id>/settings

标准请求头：
  Content-Type: application/json
  X-API-Key: myh
  Authorization: Bearer <登录接口返回的 token>

推荐调用顺序：
  步骤1：先准备 openid（注意：不要直接把 wx.login 返回的 code 当 openid 传给后端）
  步骤2：首次注册时调用 `/api/miniapp/user/register`，并设置 password
  步骤3：调用 `/api/miniapp/user/login` 获取 Bearer Token
  步骤4：后续业务接口统一携带 `X-API-Key + Authorization`

登录成功后返回：
  - token: JWT 字符串
  - token_type: 固定为 Bearer
  - user: 当前用户信息

权限规则：
  - `/api/miniapp/user/<user_id>/stats`
  - `/api/miniapp/user/<user_id>/settings`
  以上两个接口只允许访问当前登录用户自己的数据。
  也就是说，Token 里的用户身份必须和 URL 中的 user_id / openid 对应，否则返回 403。

===============================================================
二、数据库架构说明（双数据库）
===============================================================

MongoDB（原始传感器明细数据）
  - pressure_data 集合：存储每一条实时采集数据
    · device_id: 设备编号
    · timestamp: 毫秒级时间戳
    · sensors: { left_force_n, right_force_n }
    · analysis: { deviation_ratio }
    · is_seated: 是否在座

MySQL（用户数据 & 关联关系）
  - users 表：用户信息、设备绑定、久坐提醒设置、隐私设置
  - user_daily_stats 表：每日健康评分、入座时长、不良坐姿次数等

===============================================================
三、健康评分算法说明
===============================================================

健康评分 = 坐姿质量得分(满分50) + 久坐提醒合规得分(满分50)

维度1 - 坐姿质量得分 (0~50分)：
  公式: posture_score = 良好坐姿占比 × 50
  说明: 偏差比率 ≤ 10% 的数据视为"良好坐姿"

维度2 - 久坐提醒合规得分 (0~50分)：
  公式: compliance_score = (合规离座次数 / 总提醒次数) × 50
  说明: 连续入座达到阈值(默认45分钟)触发提醒，
        提醒后用户离开座位 ≥ 5 分钟视为"合规"。
        当天无久坐提醒时默认满分。

最终输出: 0~100 的整数健康评分

---------------------------------------------------------------
接口1: 获取设备实时状态
---------------------------------------------------------------
路径:   GET /api/miniapp/device/<device_id>/realtime
数据源: MongoDB
鉴权:   需要 `X-API-Key: myh` + `Authorization: Bearer <token>`

请求示例:
  Header:
    X-API-Key: myh
    Authorization: Bearer <token>
  GET /api/miniapp/device/device_001/realtime

成功响应 (200):
{
    "ok": true,
    "message": "success",
    "data": {
        "device_id": "device_001",
        "is_online": true,                    // 设备是否在线（60秒内有数据）
        "last_update_ms": 1745920000000,      // 最后数据时间戳(ms)
        "posture_status": "normal",           // "normal" | "bad"
        "posture_label": "标准坐姿 ✅",       // 中文展示文案
        "sensors": {
            "left_force_n": 320.5,            // 左侧压力值(N)
            "right_force_n": 315.2            // 右侧压力值(N)
        },
        "deviation_ratio": 0.0083,            // 偏差比率（小数）
        "continuous_seated_minutes": 23.5,    // 当前连续入座时长(分钟)
        "is_seated": true                     // 当前是否在座
    }
}

错误响应 (404):
{
    "ok": false,
    "message": "未找到设备 device_001 的数据",
    "data": null
}

前端对接要点:
  - 建议每 3~5 秒轮询一次此接口
  - is_online=false 时显示"设备离线"
  - posture_status="bad" 时前端可做红色警告提示
  - continuous_seated_minutes 超过用户设置的阈值时触发久坐提醒

七、前端开发建议
===============================================================

1. 页面结构建议：
   - 首页：设备实时状态 + 当前连续入座时长 + 久坐提醒
   - 统计页：近7天/30天趋势图 + 评分维度分析
   - 排行榜页：当日/历史排行 + 个人排名
   - 我的页：用户信息 + 设备绑定 + 久坐提醒设置

2. 实时状态轮询：
   - 建议 3~5 秒轮询 /device/<id>/realtime
   - 小程序切到后台时停止轮询，切回前台时恢复

3. 久坐提醒逻辑（前端侧）：
   - 从 realtime 接口读取 continuous_seated_minutes
   - 与用户设置的 sedentary_threshold_min 比较
   - 达到阈值时弹出提醒，建议离座休息 ≥ 5 分钟
